## Purpose

网页端测试平台：通过注册 AstrBot 自定义平台适配器，让测试消息走真实插件运行管线（filter/Handler/白名单/数据库/定时任务），为开发者和 AI 提供双向可见的模拟玩家互动消息流、消息注入接口与就地批注能力，使插件功能验证贴近真实使用环境。

## ADDED Requirements

### Requirement: 平台适配器接入真实消息管线

测试平台 SHALL 以 AstrBot 插件形式提供，并通过 `astrbot.api.platform` 的 `register_platform_adapter` 注册自定义平台适配器（适配器类型标识为 `webtest`）。注入的玩家消息 SHALL 经适配器转换为 `AstrBotMessage` 并提交到 AstrBot 事件队列，其后处理（命令过滤、白名单检查 `@require_whitelist`、忙碌状态双层检查、业务 Handler、数据库读写、定时任务）MUST 与真实平台消息完全一致，MUST NOT 绕过或模拟上述任何环节。插件通过 `event.send()` / `context.send_message()` 产生的回复与广播 SHALL 由适配器捕获并进入测试平台的可见消息流。

#### Scenario: 注入消息走真实管线

- **WHEN** 通过测试平台注入一条玩家消息"闭关"
- **THEN** 该消息经 webtest 适配器进入 AstrBot 事件队列，由修仙插件的真实 Handler 处理，回复内容与在真实聊天平台触发完全一致，且玩家忙碌状态、`user_cd` 表、数据库均按真实逻辑更新

#### Scenario: 白名单拦截行为一致

- **WHEN** 注入消息的模拟玩家不在白名单中而指令要求白名单
- **THEN** 该指令被拒绝并返回与真实平台一致的白名单提示，不执行业务逻辑

### Requirement: 与项目本体隔离，仅通过 AstrBot API 与消息管线交互

测试平台 SHALL 以独立插件目录交付，与项目本体（修仙插件）目录完全分离。测试平台 MUST NOT 修改项目本体的任何文件（代码、配置、数据、文档），亦 MUST NOT 修改 AstrBot 核心代码，且 MUST NOT 对项目本体产生任何反向影响（不写其数据、不改其配置/文件、不 patch 其模块）。测试平台与修仙插件的交互途径包括：(a) AstrBot 公开 API（`astrbot.api.platform` 等）注册并运行平台适配器；(b) 消息注入与出站消息（经 AstrBot 真实事件管线）；(c) 用户在 AstrBot Dashboard 中对修仙插件配置的手动调整（如将模拟群 ID 加入白名单，属运行时用户配置而非代码/文件修改）；(d) 为简化实现，可 import 修仙插件或 AstrBot 的模块复用其代码，但 import 不得导致对项目本体的任何写入或行为改变。测试平台 SHALL 可独立停用/卸载，卸载后修仙插件与 AstrBot 功能不受影响；其全部数据 SHALL 仅存放于 `data/plugin_data/astrbot_plugin_testplatform/` 下。

#### Scenario: 修改测试平台不影响项目本体

- **WHEN** 仅修改测试平台自身代码并重载插件
- **THEN** 修仙插件文件零变更，其行为与数据与未安装测试平台时完全一致

#### Scenario: 独立卸载

- **WHEN** 停用或删除测试平台插件
- **THEN** AstrBot 与修仙插件正常运行，无残留引用，测试平台数据保留在自身 plugin_data 子目录可整体删除

#### Scenario: 数据目录隔离

- **WHEN** 测试平台运行产生消息、批注与会话数据
- **THEN** 全部数据写入 `data/plugin_data/astrbot_plugin_testplatform/`，不触碰修仙插件的数据与配置

### Requirement: 会话与双向消息流可见

测试平台 SHALL 维护会话（会话即一个模拟对话场景，含消息历史），并提供网页界面实时展示每个会话的完整双向消息流：玩家消息、机器人回复、主动推送均按时间序呈现。消息流 SHALL 对用户（网页界面）与 AI（REST API / CLI）同时可见且内容一致。消息历史 SHALL 持久化，测试平台重启后 SHALL 可完整恢复。

#### Scenario: 双方看到同一消息流

- **WHEN** 用户在网页界面打开某会话，AI 通过 CLI 查询同一会话
- **THEN** 两者看到完全相同的消息序列（含消息 ID、时间、发送者、内容）

#### Scenario: 重启后历史恢复

- **WHEN** AstrBot 实例重启后重新加载测试平台插件
- **THEN** 所有既有会话及其消息历史、批注完整恢复，网页界面与 API 均可继续访问

### Requirement: 消息注入接口

测试平台 SHALL 提供 REST API 与 CLI 两种消息注入方式，二者行为等价。注入请求 SHALL 支持指定会话、模拟玩家与消息文本，并可选指定消息类型（私聊/群聊）。注入的消息 SHALL 被赋予真实时间戳与稳定的发送者身份，并按普通玩家消息进入管线。注入接口 SHALL 返回该消息的处理结果（机器人回复与产生的主动消息，可含延迟，因定时任务/异步结算可能稍后到达）。

#### Scenario: CLI 注入私聊消息

- **WHEN** 执行 CLI 命令向指定会话以指定玩家身份注入文本消息
- **THEN** 该消息出现在会话消息流中，对应机器人回复（如有）随后出现在同一会话，CLI 输出可读到回复内容

#### Scenario: 群聊消息注入

- **WHEN** 向群聊会话以某群成员身份注入消息
- **THEN** 消息以该成员身份进入管线，群内其他成员可见该消息与机器人回复

### Requirement: 私聊与群聊模拟

测试平台 SHALL 支持私聊会话（单个玩家）与群聊会话（多个模拟玩家共存）。模拟玩家 SHALL 可配置（昵称、ID、是否在白名单中），同一群聊会话中不同玩家 MUST 具备独立身份，使群聊语义（如针对特定成员的回复、全员可见的广播）与真实群聊一致。适配器生成的会话标识 SHALL 与真实平台会话结构一致，使依赖会话标识的插件逻辑（如"当前群"判定）正常工作。

#### Scenario: 群成员独立身份

- **WHEN** 群聊会话中存在玩家 A 与玩家 B，A 发送指令而 B 未发送
- **THEN** 插件针对 A 的状态变化只作用于 A，B 的状态不受影响，与真实群聊行为一致

#### Scenario: 白名单成员差异

- **WHEN** 群聊会话中 A 已配置为白名单成员、B 未配置，二者发送同一需白名单指令
- **THEN** A 的指令正常执行，B 的指令被拒绝并提示

### Requirement: 主动消息路由与呈现

插件通过 `context.send_message()` 向群/私聊 umo（如 `{platform}:GroupMessage:{group_id}`）发送的主动消息（定时任务广播：Boss 生成、贷款检查、悬赏过期等）SHALL 被 webtest 适配器捕获，路由到对应的模拟会话，并实时呈现在网页界面与 API 消息流中。

#### Scenario: 定时任务广播进入会话

- **WHEN** 修仙插件的 Boss 定时任务向测试平台某群聊会话的 group umo 发送广播
- **THEN** 该广播出现在对应群聊会话的消息流中，网页界面实时显示，API 可读取

### Requirement: 消息批注

用户 SHALL 能在网页界面对任意消息添加、编辑、删除批注（评论文本）。批注 SHALL 关联到具体消息，持久化存储，并 SHALL 通过 REST API / CLI 对 AI 可见，作为修改反馈依据。

#### Scenario: 批注并供 AI 读取

- **WHEN** 用户在网页界面对某条机器人回复添加批注"数值偏高，需要下调"
- **THEN** AI 通过 CLI/API 查询该会话消息时可读到该批注及所关联消息

#### Scenario: 批注随历史恢复

- **WHEN** 测试平台重启后查询曾添加批注的消息
- **THEN** 批注内容与关联关系完整保留

### Requirement: 测试会话管理

测试平台 SHALL 支持创建、切换、归档、删除会话。新会话 SHALL 提供全新的模拟玩家身份与空消息历史，使功能测试可从零状态重跑。归档会话 SHALL 保留其全部消息与批注且不再接收新注入，删除会话 SHALL 移除其数据。会话列表 SHALL 通过网页界面与 API 可见。

#### Scenario: 新会话从零开始

- **WHEN** 用户创建新会话并注入"开局指令"（如注册/初始化）
- **THEN** 该会话以全新玩家身份处理消息，不继承任何旧会话的玩家状态

#### Scenario: 归档会话冻结

- **WHEN** 某会话被归档后向其注入消息
- **THEN** 注入被拒绝或明确报错，归档会话的消息与批注保持原样可读

### Requirement: 测试用例管理与一键验证

测试平台 SHALL 提供测试用例的统一管理能力：用例 SHALL 以结构化脚本定义（含名称、**人可读的说明字段**、功能域标签、会话模板与有序步骤），步骤类型 SHALL 覆盖：注入消息、期望回复匹配（子串或正则，含超时）、等待时长。用例 MUST 携带清晰的人类可读说明：用例级 `description` 说明测试目的与覆盖场景，`scenario` 说明前置条件与涉及功能，两者为必填字段，缺少时用例 SHALL 被校验拒绝；每个步骤 SHOULD 附 `note` 说明该步骤做什么、期望什么，期望匹配步骤的 note SHOULD 描述预期行为而非仅匹配串。用例 SHALL 支持创建、编辑、列出、删除、按标签筛选与单条/批量运行。用例 SHALL 可通过网页界面创建、编辑、删除与运行（用户自助操作），编辑保存 SHALL 执行与加载器一致的校验，校验失败不得保存并给出明确错误。用例文件 SHALL 可在服务器端直接编辑，列表与运行 SHALL 从文件系统重新读取，修改即时生效。每次运行 SHALL 在全新会话中执行（默认全新玩家身份，从零状态开始），逐步骤执行并记录每步结果（通过/失败/超时/实际回复），运行结果 SHALL 持久化并可通过网页、API 与 CLI 查看，失败步骤 MUST 附带实际回复以便定位。

#### Scenario: 新增功能后快捷验证

- **WHEN** 修仙插件新增或修改功能后，用户创建带功能域标签的用例（如"闭关"用例含 我要修仙→闭关→出关 步骤）并一键运行
- **THEN** 用例在全新会话中按步骤执行，网页/CLI 可见每步通过或失败及实际回复，无需手工逐条注入

#### Scenario: 用例自解释

- **WHEN** 用户查看某用例定义或其运行轨迹
- **THEN** 可见用例级说明（测试目的/场景/前置条件）与逐步骤注释（做什么、期望什么），无需阅读代码即可理解测试意图

#### Scenario: 缺失说明被拒

- **WHEN** 提交的用例缺少必填的 description 或 scenario 字段
- **THEN** 校验拒绝该用例并给出明确错误，不参与列出与运行

#### Scenario: 用户网页自助编辑并运行

- **WHEN** 用户通过网页新建或编辑用例并保存，随后在网页发起运行
- **THEN** 校验通过则保存生效并开始运行，结果与轨迹可在网页查看；校验失败则提示错误且原内容保持不变

#### Scenario: 直接编辑用例文件生效

- **WHEN** 用户在服务器端直接修改用例 JSON 文件
- **THEN** 无需重启，下次列表或运行时按新内容生效；非法内容被校验拒绝并给出错误

#### Scenario: 多次运行互不污染

- **WHEN** 同一用例连续运行两次
- **THEN** 第二次运行使用全新会话与全新玩家身份，不继承第一次运行产生的玩家状态

#### Scenario: 期望不匹配定位

- **WHEN** 用例某步骤期望的回复子串在超时内未出现
- **THEN** 该步骤标记失败，并记录超时前收到的全部实际回复供定位

### Requirement: 测试轨迹与反馈闭环

测试平台 SHALL 为每次用例运行保留完整测试轨迹：含运行时间、用例内容快照（运行时的用例文件版本）、逐步骤结果（通过/失败/超时/实际回复），以及运行期间的全部消息交换（玩家消息与机器人回复，含时序）。轨迹 SHALL 独立于会话持久化——会话被删除后轨迹仍可查看。轨迹 SHALL 可通过网页、API 与 CLI 查看；轨迹中的消息 SHALL 可批注（复用消息批注机制），批注对 AI 经 CLI/API 可见。由 CLI/API 发起的自动化运行与网页发起的运行 SHALL 产生同等完整的轨迹。

#### Scenario: AI 发起批量测试留痕

- **WHEN** AI 通过 CLI 对某功能域标签批量运行用例
- **THEN** 每个用例运行生成完整轨迹（消息交换 + 步骤结果 + 用例快照），用户可在网页回看并按消息批注

#### Scenario: 轨迹不随会话删除丢失

- **WHEN** 某次运行的临时会话被删除后用户查看该次运行轨迹
- **THEN** 轨迹仍完整呈现该次运行的消息交换与步骤结果，且可继续批注

#### Scenario: 用例版本留痕

- **WHEN** 同一用例文件在两次运行之间被修改
- **THEN** 两次运行的轨迹各自保留运行时的用例内容快照，可对比差异

### Requirement: 访问控制

测试平台 Web 服务 SHALL 默认仅监听本机回环地址。对 REST API 的写入操作（消息注入、会话管理、批注修改）SHALL 在启用访问令牌时校验令牌，未提供或错误令牌 SHALL 返回 401。读取操作遵循同一令牌策略。平台 MUST NOT 引入账号/角色系统。

#### Scenario: 令牌校验

- **WHEN** 未携带令牌或携带错误令牌调用消息注入 API
- **THEN** 请求返回 401 且消息不进入任何会话

#### Scenario: 本机默认访问

- **WHEN** 未配置令牌且从本机访问网页界面
- **THEN** 界面正常加载并可查看消息流
