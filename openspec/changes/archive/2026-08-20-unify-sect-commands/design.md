# Design: unify-sect-commands

## Context

宗门功能现分散在 18 个顶层指令（`main.py:115-131` 常量区 + `main.py:1074-1220` 路由区），宗门专属悬赏在 `handlers/bounty_handlers.py:36-44` 以「🏯 宗门悬赏」分区混入全局悬赏令。AstrBot 指令名不能带空格（空格后内容会被解析为参数），因此「宗门」注册为单一指令、第一个参数作子命令名是符合框架约束的自然形式。悬赏底层存储（`player_bounties` 表）全局与宗门共用，且 `BountyManager.accept_bounty` 强制"同一玩家同一时间仅一个进行中悬赏"（`managers/bounty_manager.py:308-313`）。

前序 change `add-default-sects-and-sect-growth` 尚未归档，其 `sect-system` delta 中「宗门内容联动」关于悬赏榜呈现的描述（"带归属的悬赏仅出现在对应宗门成员的悬赏榜"）将被本 change 改变；`openspec/specs/` 尚无 `sect-system` 主 spec。

## Goals / Non-Goals

**Goals:**

- `/宗门` 单指令 + 子命令路由覆盖全部宗门功能，含宗门排行/贡献排行。
- 宗门悬赏全生命周期（查看/接取/进度/完成/放弃）在 `/宗门 悬赏` 下闭环；全局悬赏指令完全不再触碰 `sect_id` 悬赏。
- 宗门专属秘境仅本宗成员可见；新增 `/宗门 商店` 宗门专属商店（贡献点结算）；历练宗门事件结算带显性标记。
- 业务逻辑零重写：只搬入口与分流，复用现有 `SectManager`/`BountyManager`/`RankingManager` 方法。

**Non-Goals:**

- 不改悬赏底层存储结构、"单活跃悬赏"约束与行为计数挂钩逻辑。
- 不改秘境准入校验、历练事件过滤/抽取权重、领悟池注入、职阶福利（签到加发/全局商店折扣）等联动语义。
- 不改全局商店/阁楼的商品池与刷新机制。
- 不保留旧指令兼容别名（用户已确认全部移除）。

## Decisions

### 1. 子命令分发器放在 `SectHandlers`

在 `handlers/sect_handlers.py` 新增 `handle_sect_entry(event, args)` 分发方法：`main.py` 只注册一个 `@filter.command(CMD_SECT := "宗门")`，参数透传。分发器内部维护 `子命令名 → 处理函数` 映射表，缺参/未知子命令输出导航帮助。备选方案是 `main.py` 里写巨型 if-elif——否决，路由表集中在 handler 便于维护与单测。

子命令命名直接沿用原指令去掉"宗门"前缀的习惯叫法：创建/加入/退出/信息/列表/捐献/任务/丹房/建设/镇派功法/晋升/宝库/师承/踢出/传位/职位/排行/贡献排行/悬赏。

### 2. 宗门悬赏逻辑复用 `BountyManager`，按类型分流

不新建 manager。`BountyManager` 增加类型维度：

- `get_bounty_list` 拆为全局/宗门两个视图（宗门视图按玩家所属宗门 `sect_id` 过滤）。
- `accept_bounty` 增加来源校验：全局入口拒绝 `sect_id` 悬赏（提示走「宗门 悬赏 接取」），宗门入口仅接受本宗 `sect_id` 悬赏。
- `check_bounty_status`/`complete_bounty`/`abandon_bounty` 操作"当前活跃悬赏"时校验其类型归属：全局指令遇宗门悬赏、宗门子命令遇全局悬赏，均拒绝并提示对方入口。
- `add_bounty_progress` 的完成提示语（`bounty_manager.py:584` 硬编码 `/完成悬赏`）按模板类型分别指向 `/完成悬赏` 或 `/宗门 悬赏 完成`。

**"单活跃悬赏"约束保持全局共享**：接取任一类型都会阻塞另一类型，拒绝文案提示先完成/放弃当前悬赏。备选方案"允许全局+宗门各一个活跃"会改动存储约束与计数挂钩，超出入口拆分范畴——否决。

**校验顺序：类型/归属校验先于冷却与活跃检查**。`accept_bounty` 及状态/完成/放弃的类型归属校验必须最先执行——否则玩家带着放弃冷却或活跃悬赏时，跨类型操作会报冷却/活跃而非分流提示，入口引导与功能测试断言都变得不确定（分流用例的确定性依赖此顺序）。

### 2.1 GM「清除悬赏」测试辅助

新增 GM 子命令清除目标玩家的进行中悬赏记录（`player_bounties`，按放弃语义移除、不发奖励）与放弃冷却（`system_config.bounty_abandon_cd_<uid>`）。动机：功能测试的生命周期/分流用例放弃悬赏后产生 30 分钟冷却，同轮批跑内后续用例与 `--repeat` 重跑均被拦截；fixture 只能保证批跑起始状态，无法解决用例间污染。遵循「清除CD」的确认二次确认与数字 ID 定位模式。备选"fixture 删表"——否决，解决不了同一轮内污染；备选"用例排序规避"——否决，顺序耦合脆弱。

### 3. 忙碌状态白名单不加「宗门」

`BUSY_STATE_ALLOWED_COMMANDS` 用 `startswith` 匹配（`handlers/utils.py:131`），若把「宗门」加入白名单会让"任务/捐献"等操作类子命令在修炼中也可用。保持现状不加：忙碌时全部宗门子命令被拒，与今天各独立宗门指令均不在白名单的行为一致（parity）。"宗门 信息/排行"忙碌时不可用属于可接受的既有语义延续。

### 4. 与未归档 change 的 spec 关系

`add-default-sects-and-sect-growth` 必须先归档（其 `sect-system` delta 落地主 spec），本 change 归档时以 `sect-commands` 新 capability 叠加；届时需手工核对主 spec「宗门内容联动」中悬赏榜呈现的措辞与本 change 一致（归档时同步修正）。若顺序反过来，`sect-commands` 先归档无冲突（独立 capability 路径），后归档的 sect-system delta 措辞会过期——以归档脚本/人工核对兜底。

### 5. 宗门秘境可见性：列表层过滤而非标注

`rift_manager.py:list` 目前对非本宗成员显示 🔒 锁定条目。改为在列表渲染前按 faction_id 过滤掉 `sect_id + access=sect_member` 且不匹配的秘境；`_check_sect_access` 准入校验保持不变作为兜底。备选"保留 🔒 标注"——否决，用户明确要求仅本宗可见，且隐藏可避免泄露他宗专属内容的存在。

### 6. 宗门商店：独立商品池 + 贡献点结算

商品池配在 `sect_factions.json` 各宗门 `shop` 字段（与传承 `treasure`/`heart_methods` 同文件同风格），条目引用既有物品配置（武器/防具/心法/丹药 id）+ `price`（贡献点）+ 可选 `min_position` 职阶门槛。结算货币定为**宗门贡献点**：现状贡献点只有晋升门槛一个出口（宝库是职阶资格免费领取、无消耗），商店给贡献提供消耗回路，形成"捐献/任务 → 贡献 → 商店/晋升"的宗门内部经济闭环。备选"灵石结算"——否决，会与全局商店同质，且无法体现宗门专属感。购买逻辑放 `SectManager`（贡献字段在它手里），职阶折扣沿用 `ShopManager.get_sect_shop_discount` 不复用（折扣作用于灵石价格，贡献商品价格由策划直接配死，避免双重经济参数）。

### 7. 历练宗门事件标记：展示层最小改动

`adventure_manager.py:334` 结算消息仅拼 `event['desc']`。改为事件带 `sect_id` 时前缀「🏯 宗门际遇 · {事件名}」；抽取/过滤逻辑（`_build_event_weight_pool`/`_filter_group_events`）一行不动。备选"在 desc 文案里由策划手写标记"——否决，依赖配置自觉，代码层兜底更可靠。

## Risks / Trade-offs

- [18 个旧指令一夜失效，老玩家困惑] → `/修仙帮助` 宗门章节重写为新入口对照表；「宗门」无参数导航帮助自解释。
- [子命令与玩家参数混淆，如「宗门 逍遥门」] → 分发器对未识别首参统一回导航帮助，并提示"若要加入宗门请用 /宗门 加入 逍遥门"类引导（对常见误用首参做友好提示）。
- [悬赏双向拒绝提示遗漏某条路径，玩家持有宗门悬赏却只能用全局指令] → 分流校验集中在 `BountyManager` 一处实现，两侧入口共用，测试覆盖全部交叉组合。
- [全局与宗门共用活跃悬赏槽位，玩家以为可并行] → 接取拒绝文案明确说明"先完成或放弃当前悬赏"，两类入口提示一致。
- [宗门秘境隐藏后非本宗玩家不知其存在，内容曝光度下降] → 有意为之（用户要求）；宗门宣传由「宗门 列表」/宗门介绍承载。
- [贡献点新增消耗出口引发通胀/通缩失衡] → 商品价格与职阶门槛全走 `sect_factions.json` 配置，策划可调；商店不参与随机折扣，价格确定性可控。

## Migration Plan

无数据迁移。部署即代码更新 + 热重载；回滚即还原 git 提交并重载插件。功能测试用例（`functional_tests/cases/` 宗门/悬赏域）同步改写为新指令形式后重跑。
