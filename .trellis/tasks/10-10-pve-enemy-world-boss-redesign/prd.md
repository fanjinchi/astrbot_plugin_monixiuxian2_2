# PVE 怪物与世界 Boss 重做总规划

## Goal

把已在 `design_docs/content-design/pve-enemy-design.md` 封板的 PVE 战斗设计，拆成可独立实现、验证和回滚的工程任务，最终让固定敌人名册、玩家持续气血、普通 PVE 结算以及世界 Boss 生命周期在真实运行时中与设计验收口径一致。

用户价值：玩家面对的怪物强度和差异不再由旧经验值公式临时派生；战斗损耗能够跨场保留并自然恢复；世界 Boss 成为有限次数、多人累计贡献、可恢复生命周期的全服玩法。

## Requirements

### R1. 规划与内容治理

- 总任务必须映射为六个可独立验收的子任务（气血、固定目录、持久化/事务基座、普通 PVE、世界 Boss、集成），明确依赖顺序、集成门和回滚边界。
- 已封板的数值/机制与仍为占位的叙事状态必须分别标识，不能用工程实施默认为内容定稿。
- 正式敌人内容只能通过 `scripts/sync_content_to_config.py` 从 `design_docs/` 导入，禁止手改生成配置。
- 守护者继续使用动态匹配兼容路径；本轮不宣称完成守护者胜率锚。

### R2. 玩家持续气血

- 采用三层权威命名：`base_hp` 是永久基础气血，`current_hp` 是当前持久气血资源，`max_hp` 是运行时计算的最终上限（`base_hp` + 装备/功法/其他加成）。
- 旧数据库 `hp` 必须无损迁移为 `base_hp` 并新增 `current_hp`；不得保留语义含混的 `hp` alias，避免新代码继续误用。
- 创角、突破、装备、丹药、商店、GM、PvP、普通 PVE、秘境和世界 Boss 必须统一消费新的气血契约。
- 恢复按每分钟动态 `max_hp` 的 1% 惰性计时，**全时段计时、不判断忙碌**（2026-10-12 用户改口径，取消「仅空闲」闸门；历练/修炼/秘境/pending 期间一律照常恢复，闭关出关不再被剥夺回血）。由于权威 `user_cd` 每用户仅保留当前一行，状态转换前仍先惰性结算并推进持久锚点（目的是让 `current_hp` 与锚点落库一致，不再是「消费掉忙碌时长」），不声称事后重建历史活动区间；不依赖 per-player 常驻定时器；不得把 `players.state` 镜像当唯一依据。恢复锚点不登记 GM 时间快进。
- 装备或增益导致动态最大气血下降时，`current_hp` 必须被钳制到 `[0, max_hp]`；突破只增长 `base_hp`，战斗和恢复只读写 `current_hp`。
- PVE 败场结算保留气血地板（**2026-10-12 由 25% 下调为 `ceil(1% * 动态 max_hp)`，胜场不保底；历练与世界 Boss 统一适用**），并与持久疲劳（路线基础 `fatigue_cooldown` 300/600/900/1200 秒恒定 + 仅真实战败追加 600 秒）和身法逃跑规则保持设计一致。

### R3. 固定敌人名册运行时

- 28 只固定名册敌人必须按设计段位和绝对面板生成，不再由旧 `exp_needed`、类别倍率、随机等级或 ±10% 属性抖动重建。
- 运行时敌人战斗档案必须完整携带 `level_index`、暴击、词缀、触发技能、护甲及基础五维，并一致映射为 `FighterState`。
- `difficulty_coefficients` 等无消费者的旧路径必须移除；全局难度活旋钮的作用属性必须只有一个权威定义。
- 守护者和秘境定向怪物组不得因普通名册切换而退化。
- CSV、同步生成配置、运行时 Enemy 和 Fighter 之间必须有一致性测试。

### R4. 普通 PVE 规则

- 普通、精英和组内 Boss 的选择、胜负、TTK、当前气血回写、失败保底、疲劳及逃跑规则必须按封板设计执行。
- 逃跑首版只对高/极高风险历练开放，在战斗前给玩家一次主动选择：成功则不进入战斗、`current_hp` 不变、本次历练机会消耗且路线基础收益照常结算，不产生击败事实或战败疲劳；失败则锁定同一只敌人立即正常开战，不得重复尝试或重掷敌人。
- 逃跑成功率必须为玩家/敌人身法关系的单调有界函数，具体系数经地板/标模/天花板模拟收口后写回权威设计；不得在工程实现中临时手拍。待选择状态必须可在重启后恢复并幂等消费，不能复用现有零惩罚、进程内的 `EncounterStore`。
- 待选择首版不自动过期：玩家在迎战或逃跑终态提交前保持历练 busy，**用途是挡住「开始历练」**；终态必须原子清除 busy。此约束避免「放置坏遭遇后重开路线」。（原「利用等待触发空闲回血」的担忧随 R2 全时段恢复口径一并取消，pending 不需要改写 `user_cd.scheduled_time`。）
- 路线疲劳必须持久化（写端与休整读端两端都切，不得继续以 `AdventureManager._route_cooldowns` 内存状态为权威）并纳入 GM 时间快进；构成为「基础休整时长按所走路线取值（scout 300 / journey 600 / hunt 900 / peril 1200 秒，胜负都追加）+ 仅真实战败再 +600 秒，写入取 `max` 不回退」，取消现网路线事件 `injury` 触发的 +600 分支。**疲劳粒度为每人一份全局窗口**（休整期内任何路线都不能开；乙案，2026-10-12 拍板）——这是对旧实现按路线独立休整的有意玩法收敛，旧语义从未成文；随之必须把「该路线尚在休整中 / 该路线休整 X 分钟」两处玩家文案改为全局表述。上述构成与粒度此前均未记录在 `design_docs`，已一并补写进 `pve-enemy-design.md` §Q4。
- 运行时验收必须复用或等价复现设计模拟器的玩家标模和统计口径，防止“模拟通过、配置映射漂移”。
- 在 Step 7 完成前，不得以临时奖励数字冒充正式经济设计。

### R5. 世界 Boss 生命周期

- 世界 Boss 从 4 只固定名册中生成，境界段随机，完整出生面板必须持久化并可在重启后无损恢复。
- 每个实例必须具有明确的 `active -> defeated | dissipated` 状态转换、48 小时存活期，以及击杀后 12 小时/消散后 24 小时的下次生成资格。
- 每名玩家每日最多挑战 3 次；每日按 `Asia/Shanghai`（北京时间）00:00 重置，部署机器时区不得改变规则；相关绝对时间戳必须纳入 GM 时间快进覆盖。
- 每场结算必须原子更新 Boss 当前气血、玩家当日次数、真实本场伤害、累计伤害和阶段；并发挑战不得超扣气血、超次数或产生多个末击者。
- 三阶段阈值及属性变化必须按设计执行；阶段/击杀/消散先产生唯一业务事件，再按 platform/group 建 per-destination delivery。平台不支持 dedupe 时不承诺接收端 exactly-once；已 sent 目标不因其他目标失败重播，结果不确定目标进入人工处置。
- Boss 结算必须产生可幂等消费的奖励资格/结算记录，使 Step 7 可以随后接入而不重写战斗事务。

### R6. 奖励边界（本轮仅预留，不实施 Step 7）

- Step 7 的丹药、材料、普通/精英/组内 Boss 掉落以及世界 Boss 分账数值，延后到正式秘境设计完成后统一做经济总账；本轮不得自行填入临时正式数值。
- 本轮只定义稳定的战斗结算输出和世界 Boss 贡献/末击事实，使后续奖励模块无需重写战斗事务即可消费。
- 若现有经验/灵石奖励是保持当前开发流程所必需，必须明确标为兼容行为且不得扩展为新经济设计；最终由 Step 7 统一替换或确认。
- 后续奖励发放必须可幂等重试，经济内容仍须经 `design_docs/` 用户确认和同步管线导入。

### R7. 兼容、文档与质量

- 数据库迁移必须覆盖旧玩家和已有 Boss 数据，并提供失败回滚/重试策略。
- 更新与实现不一致的 `design_docs/project-architecture.md`、`design_docs/current-design-report.md`、`design_docs/README.md` 及相关 API 文档。
- 每个子任务必须包含定向单元测试；总集成必须通过 `uv run ruff format .`、`uv run ruff check .` 和 `uv run python -m pytest tests/ -v`。
- 真实 webtest 只在用户明确要求时运行；项目内功能用例应扩充次数、阶段、台账、消散、重启恢复和奖励幂等场景。

## Resolved Product Decisions

- 项目尚未上线，本轮可以规划并实现除 Step 7 外的全部战斗与基础设施，无需维持长期新旧双运行；但正式固定内容未批准前旧开发入口仍维持原状，新入口保持 disabled，获批后的激活检查点再原子停旧启新。仍必须保证开发数据库迁移可重复验证。
- Step 7 延后到正式秘境设计完成后，与丹药、材料和各玩法产消统一规划。此决定合理，因为当前最缺的是跨玩法材料用途和总产出预算；提前确定掉落会在秘境完成后高概率返工。
- 本轮世界 Boss 仍应保存贡献、档位输入和末击事实，但不发明最终分账价值，以避免将战斗状态机与奖励经济耦合。
- 世界 Boss 每日次数以 `Asia/Shanghai` 的自然日为唯一日期边界，避免服务器部署时区变化影响玩家规则。
- 气血采用 `base_hp` / `current_hp` / 动态 `max_hp` 三层命名，旧 `hp` 迁移后不保留兼容别名；此决定避免把永久基础值误称为会受装备变化的最终上限。
- 逃跑首版采用高/极高风险战斗前一次主动判定：成功跳过战斗并保留路线基础收益，失败锁定同一敌人开战；公式参数须经模拟另行封板。
- **2026-10-12 追加决议（C 规划审查）**：① 惰性气血恢复取消「仅空闲」闸门，改全时段计时（连带使 pending 不必改写 `user_cd.scheduled_time`，`BusyState` 不需要新 API；闭关出关接近满血是该口径的直接后果，已知情）；② 历练基础休整时长（按所走路线取 300/600/900/1200 秒）**保留**，仅取消路线事件 `injury` 的 +600 分支，战败 +600 保留；③ child C 获准用 **v39** 为 `adventure_settlements` 增 `state`/`route_key`/`snapshot` 列（走共享建表函数保持 fresh==upgrade parity），因为 v36 冻结的只是事实账本、v37 世界 Boss 表才是状态机形态，两者不对称；④ 历练副作用消费采用「提交后 inline claim」而非 v38 广播 outbox——历练消费者都是本地调用，套投递队列是过度设计；⑤ 迎战/逃跑指令定名为顶层 `迎战`、`逃跑`；⑥ 疲劳粒度定**乙案 = 每人一份全局窗口**（一条路线的休整挡住所有路线；这是对旧实现按路线独立休整的有意收敛，旧语义从未成文，随之「该路线尚在休整中」等玩家文案必须改为全局表述；`adventure_fatigue` 表与基座单行 API 不动，v39 不涉及疲劳表）；⑦ 逃跑参数未封板时**战前选择面整体 disabled**（完成时直接进战斗，不产生 `pending_choice`，避免玩家空发一条「迎战」却毫无选择收益）。
